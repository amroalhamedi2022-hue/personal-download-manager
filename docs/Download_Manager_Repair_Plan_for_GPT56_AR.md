# خطة إصلاح وتسليم مدير التحميل إلى GPT‑5.6 Sol

تاريخ الخطة: 19 أكتوبر 2026. الحالة عند التسليم: **خطة جاهزة للتنفيذ؛ لم تُنفذ إصلاحاتها بعد**.

هذه الخطة تحول ملاحظات إعادة التدقيق إلى دفعات عمل واختبارات قبول. وهي ملحق تنفيذي للمرجع الإلزامي `docs/Download_Manager_Execution_Plan_v1.md`، ولا تستبدله أو تختصر نطاقه. يبقى مجلد `docs/design` مرجع التصميم المعتمد. جميع بنود الخطة الأصلية الـ82 محفوظة، بما فيها المؤجل.

## 1. ابدأ من هنا

1. اقرأ هذا الملف كاملًا، ثم اقرأ النسخة الحالية الكاملة من `docs/Download_Manager_Execution_Plan_v1.md` وجميع وثائق `docs/design` ذات الصلة، وافحص صورة النافذة المعتمدة بصريًا. اقرأ تقرير `Download_Manager_Recheck_2026-10-19_AR.md` كاملًا إن كان مرفقًا؛ هذا الملف يتضمن تحويل جميع نتائجه A01–A14 وR01–R06 إلى عمل قابل للتنفيذ.
2. اقرأ أي `AGENTS.md` ينطبق على الملفات قبل تعديلها. افحص Git والملفات غير المحفوظة والفروع البعيدة قبل اختيار نقطة البدء. لا تعتبر سجل المحادثة أو نسخة محلية قديمة مصدرًا أحدث من المستودع الفعلي.
3. نفّذ RF00 أولًا، ثم RF01. لا تبدأ بالألوان أو ميزات جديدة بينما أخطاء الإيقاف واستعادة Retry مفتوحة.
4. بعد كل دفعة: اختبارات مناسبة، مراجعة فرق الكود، Commit واضح، تحديث المرجع الإلزامي بدليل الإنجاز والخطوة التالية. انتقل إلى الدفعة التالية المتاحة دون انتظار كلمة «كمل».
5. إذا انتهى السياق، احفظ نقطة الاستئناف بالقالب في القسم 10. يستأنف النموذج التالي من أول اختبار قبول غير ناجح، ولا يعيد المشروع من البداية.

**هدف أول دورة:** جعل الاستعادة والطوابير وRetry والإيقاف والبيانات آمنة ومثبتة باختبارات حقيقية. **هدف ما بعدها:** إكمال النواقص الأصلية بالترتيب حتى قبول Windows ومثبت EXE. وجود EXE مبني حاليًا لا يساوي تحقيق الهدفين.

## 3. قواعد ثابتة تحمي العمل السابق

- استخدم المستودعين الموجودين؛ لا مستودع GitHub جديد ولا إعادة إنشاء التطبيق أو تغيير تقنيته من الصفر.
- حافظ على الملفات والكود والميزات والتصميم المعتمد. الإصلاحات موضعية في مواضع الخلل، مع حفظ الأصل في Git ونقطة استرجاع. لا حذف ملفات أو استبدال منظومات واسعة أو إسقاط متطلبات لتسهيل الإغلاق. إذا احتاج الإصلاح إزالة كود موجود خلافًا لهذا القيد، اشرح الموضع والبديل واحصل على توجيه محدد قبل تلك الإزالة، وواصل العمل المستقل المتاح.
- لا تستخدم `reset --hard` أو تنظيفًا شاملًا أو Force Push أو تغيّر بيانات المستخدم الأصلية أثناء التجارب. لا تمحُ تعديلات لا تعرف مصدرها.
- قبل تغيير كبير: نقطة مصدر قابلة للاسترجاع عند الرأس الفعلي. قبل تغيير تخزين: نسخة **بيانات** أيضًا، منفصلة عن Git، بصلاحيات مناسبة، مع تجربة استعادة على بيانات مصطنعة. فرع Git لا يحفظ تنزيلات المستخدم أو أسراره.
- لا تدخل كلمات مرور أو Cookies أو مفاتيح أو ملفات بيانات المستخدم في Git أو تقارير التسليم. استخدم أسرارًا اختبارية مصطنعة وفحصًا منقحًا للسجلات.
- احتفظ بأدلة E001–E025 التاريخية مع بيان نطاقها؛ أضف دليلًا جديدًا بالرقم التالي المتاح. لا تدّع أن نجاح Build يثبت اختبار واجهة أو أمان أو تثبيت.
- لا تضف إطار عمل/اعتمادًا ضخمًا أو تغير نسخ المكتبات بلا حاجة مرتبطة بإصلاح. عند الحاجة، افحص الترخيص والمصدر الرسمي وتوافق التغليف.
- لا تبدأ Android أو Torrent أو اختيار مواقع جديدة تلقائيًا؛ تبقى في الخطة وفق شروطها. تأجيل اختيار المواقع لا يمنع إطار Plugins وبيئة الاختبار المحلية.

## 6. بطاقات التنفيذ التفصيلية

### RF00 — تثبيت الحقيقة قبل كتابة الإصلاحات

**المطلوب:** جلب آخر حالة للمستودعين، فحص `git status` وCommits والفروع وملفات P2-10، حفظ أي عمل غير ملتزم دون تنظيفه، ثم إنشاء نقطة استرجاع جديدة تحمل الرأس الفعلي قبل الإصلاح. أبقِ فرع النسخ التاريخي كما هو. سجل SHA ونوع النسخة المحلية وأي فرق عن التدقيق.

**في المرجع الأصلي:** أضف قسم متابعة إصلاحات يربط هذا الملف والتقرير. حدّث الملخص المتعارض وبصمات المصدر والحزمة. أعد P2-10 إلى «جزئي/قيد التحقق» مع حفظ E025 كدليل ناجح في نطاقه، وسجل إعادة تحقق P2-07 بعد Restart. P2-05 مفتوح أصلًا؛ سجل عيوبه دون الادعاء أنه كان مغلقًا. أبقِ P2-09 وأدلته، وأعد فحصه عند أي تغيير حسابي/مرئي لاحق.

**اختبار C00:** توجد قراءة كاملة للخطة والتصميم، ومصدر معروف ونقطة استرجاع وسجل فرق؛ لا رقم اختبارات جديد دون XML. إذا كانت الملاحظات أُصلحت في HEAD أحدث، اربط الإصلاح واختباره بدل تكراره. إذا تعذر الوصول للمستودع، اذكر العائق؛ لا تصنع مشروعًا بديلًا من الذاكرة.

### RF01a — دورة حياة واحدة وإيقاف لا يترك تشغيلًا خلفه

**مواضع البداية، بالنسبة إلى جذر المستودع:**

- `downloader/core/src/commonMain/kotlin/ir/amirab/downloader/DownloadManager.kt`
- `downloader/core/src/commonMain/kotlin/ir/amirab/downloader/downloaditem/DownloadJob.kt`
- `downloader/core/src/commonMain/kotlin/ir/amirab/downloader/downloaditem/http/HttpDownloadJob.kt`
- `downloader/core/src/commonMain/kotlin/ir/amirab/downloader/downloaditem/hls/HLSDownloadJob.kt`
- `shared/app/src/commonMain/kotlin/com/abdownloadmanager/shared/util/DownloadSystem.kt`

**الإصلاح:** اجعل الحصول/الإنشاء لمهمة بالمعرف نفسه ذريًا، ونسّق Resume/Pause/Reset/Delete/Retry عبر قفل دورة حياة محدود أو آلية مكافئة. لا تمسك قفل مدير عام أثناء انتظار شبكة أو قرص. استخدم رقم جيل أو رمز صلاحية لإبطال callback قديم إذا لزم؛ لا تعتمد فقط على إلغاء مؤقت لم يُسجل بعد. اجعل أي إلغاء وانتظار انتهاء واضحين مع تجنب انتظار coroutine لنفسها.

عرّف معنى حالات الانتظار والنشاط في جدول انتقالات صغير داخل التوثيق. يجب ألا يظهر تنزيل شبكي يعمل و`isDownloadActive=false`. لا تعالج ذلك بجعل كل مهمة منتظرة «تنقل بايتات». ميّز نية التشغيل والانتظار وحجز slot والعمل الشبكي، ثم اجعل مستهلكي الحالة متفقين.

Stop All يشمل المهام النشطة والتحضير والاستئناف وRetry والطلبات المنتظرة، ويمنع إدراج عمل جديد ضمن نفس عملية الإيقاف حتى تستقر. انتظر توقف الطوابير والعمال والمؤقتات ذات الصلة، وامسح نية Retry عند الإيقاف الصريح للمستخدم. الخروج الطبيعي مسار مختلف: يحفظ نوايا الاستئناف المسموح بها وفق سياسة موثقة، دون بدء نقل أثناء الإغلاق. لا تستخدم مسح Retry في Stop All كسبب لفقد نية الاستعادة عند الخروج.

**القبول:** C04–C07. راجع تغيير الوجهة أثناء النشاط، وتحرير تصاريح الاتصالات، وعدم إطلاق حدث إكمال عند مجرد توقف/انتظار. سجل نتائج HTTP وHLS منفصلة.

### RF01b — الاستعادة تعيد الأهلية ولا تتجاوز مالك الطابور

**المواضع:** الملفات السابقة، و`downloader/core/src/commonMain/kotlin/ir/amirab/downloader/queue/DownloadQueue.kt` و`ManualDownloadQueue.kt` و`QueueManager.kt`، ومسار Boot في `DownloadSystem.kt`.

**الإصلاح:** اكتمال مهلة Retry لا يمنح إذن تنزيل مباشرًا. استعد الموعد والمحاولة مرة واحدة، ثم مرر المهمة إلى آلية القبول القائمة: عضوية الطابور، حالته، نافذة الجدولة، حدود عدد الملفات، وحدود الموقع/الملف. لا تُنشئ طبقة جدولة بديلة منافسة. حرر/أعد حجز التصاريح حسب سياسة الانتظار الموثقة؛ المهم ألا تتجاوز أي سقف وألا تتسرب التصاريح.

جهّز الطوابير والتصنيفات والمستمعين وحارس الإقلاع قبل أن تستطيع Retry مستحقة فورًا بدء نقل أو إطلاق إكمال. اختر سياسة واضحة للموعد الفائت، وتغير الساعة، وSleep/Wake؛ لا تجعلها تتجاوز طابورًا متوقفًا أو جدولًا غير فعال. القديم الذي لا يحمل حقول Retry يظل قابلًا للقراءة.

**القبول:** C01–C05، مع خادم HTTP محلي وHTTP/HLS Job فعليين. Fake Job يصلح لفحص وحدة ضيق؛ لا يغلق هذه الدفعة وحده.

### RF02 — محاولات محدودة واحترام مهلة الخادم عبر كل الطبقات

**المواضع:** `downloaditem/RetryPolicy.kt` و`downloaditem/http/HttpDownloadJob.kt` و`downloaditem/hls/HLSDownloadJob.kt` و`part/PartDownloader.kt` و`part/HttpPartDownloader.kt` تحت `downloader/core/src/commonMain/kotlin/ir/amirab/downloader/`.

**الإصلاح:** لا تصفّر عداد الفشل بمجرد نجاح Metadata أو إنشاء العمال. عرّف تقدمًا حقيقيًا ومتى يبدأ budget جديد؛ وثّق الفرق بين المحاولة الأولى وعدد الإعادات حتى لا يحدث خطأ واحد زائد. لا تسمح لاستئناف العملية أو فشل أجزاء متكرر بتجاوز الميزانية. احفظ الحالة في نقاط انتقال محددة.

راجع مسار فشل أول Resume ومسار إعادة الجزء الداخلي؛ كلاهما يجب أن يصل إلى سياسة الأخطاء الصحيحة. HTTP 429/503 و`Retry-After` لا يضيعان في نوع استثناء عام أو CancellationException. يجب ألا توجد إعادة داخلية ثابتة كل ثانية تنتهك مهلة الخادم قبل وصول الخطأ إلى Job.

افصل سقف backoff المحلي عن الحد الأدنى الذي طلبه الخادم. `Retry-After: 3600` لا يُختصر إلى 900 ثانية ثم يرسل طلبًا مبكرًا. للمدد الكبيرة جدًا استخدم انتظارًا محفوظًا أو توقفًا واضحًا يحتاج قرار المستخدم، مع معالجة Overflow وقيم Header الخاطئة. استخدم الزمن الافتراضي للاختبارات الطويلة. إذا كانت السياسة تتطلب تهدئة Host مشترك، اختبر عدم تجاوزها بملف آخر دون تعطيل مضيف مستقل.

**القبول:** C08–C12؛ لا يكفي اختبار دالة حساب التأخير. اختبر طلبات فعلية وعدادات الطلب عند الخادم.

### RF03 — سلامة التخزين والقراءة والخروج

**المواضع:**

- `downloader/core/src/commonMain/kotlin/ir/amirab/downloader/db/TransactionalFileSaver.kt`

- `shared/app/src/commonMain/kotlin/com/abdownloadmanager/shared/util/category/CategoryManager.kt`
- `desktop/app/src/main/kotlin/com/abdownloadmanager/desktop/AppComponent.kt`

**الإصلاح:** ميّز ملفًا غير موجود عن قائمة صحيحة فارغة وعن JSON تالف وخطأ IO/صلاحيات ونسخة Schema غير مدعومة. لا تحول فسادًا إلى `emptyList()` ثم تحفظها تلقائيًا فوق الأصل. احتفظ بالأصل التالف ونسخة سليمة إن وجدت، واعرض مسار استرجاع مفهومًا. لا تخفِ سجل تنزيل تالفًا وكأنه لم يوجد؛ راجع أثر `mapNotNull` في قراءة القائمة ضمن نفس مبدأ عدم فقد الدليل.

أصلح fallback الخاص بالحفظ بحيث لا يحذف آخر نسخة ملتزمة سليمة قبل وجود بديل قابل للاسترجاع. اكتب مؤقتًا وتحقق من اكتماله، ثم استبدل وفق قدرات filesystem مع backup/journal مناسب. لا تبنِ تحديد «عدم دعم atomic move» على نص رسالة استثناء وحده إذا أمكن تصنيف أدق. أي ادعاء دوام بعد انقطاع الطاقة يحتاج ضمانات منصة واختبارًا مستقلًا؛ flush وحده ليس شهادة بذلك.

أضف مسار `flush/close` واضحًا لآخر تغييرات التصنيفات والطوابير والـMetadata عند الخروج الطبيعي. انتظر الحفظ قبل `exitProcess`، وأظهر فشل الحفظ بدل تجاهله. لا تجعل مدة انتظار عشوائية 500ms حلًا. قتل العملية قد يفقد آخر تغيير غير ملتزم فقط حسب سياسة موثقة، ولا ينبغي أن يدمر آخر لقطة ملتزمة.

**القبول:** C13–C17. جميع اختبارات التلف/رفض الكتابة/الانقطاع في مسار بيانات اختبار معزول، لا مجلد المستخدم الحقيقي.

### RF05 — حماية أسرار Windows وترحيل قابل للاسترجاع

الترحيل: نسخة بيانات قبل البدء، قراءة الصيغة القديمة، حفظ السر المحمي والتحقق من إمكان قراءته، ثم الالتزام بمرجعه ووسم النسخة. لا تحذف الأصل قبل نجاح العملية. وثق رجوع إصدار قديم: استرجاع نسخة ما قبل الترحيل هو المسار الآمن إن لم يفهم Schema الجديد؛ لا تعد بإمكانية الرجوع المباشر بلا اختبار. تعطل مخزن الأسرار يطلب إعادة إدخال ولا يعود لحفظ نصي صامت.

التصدير والنسخ المحمولة الافتراضية غير سرية. قد لا تنتقل أسرار DPAPI بين حسابين/جهازين؛ اعرض ذلك بوضوح واختبر السلوك، ولا تحول فشل فكها إلى فقد تنزيل. حافظ على البيانات القديمة في نسخة استرجاع محمية محليًا، لا في المستودع أو تقارير التشخيص.

### RF07 — الاستكمال وهوية الملف

**الإصلاح:** تساوي الحجم ليس إثباتًا لهوية المحتوى. استخدم Validator مناسبًا حسب HTTP، وميّز ETag القوي والضعيف؛ احفظ Last-Modified إن استُخدم وافهم محدوديته. استخدم شروط الطلب المناسبة، وعالج 200 بدل 206 وتغير الحجم/المحتوى برفض دمج القديم بالجديد. عند غياب دليل كافٍ للاستكمال أو Refresh، قدم خيارًا محافظًا واضحًا لإعادة التنزيل/تدخل المستخدم مع الحفاظ على الجزء السابق.

**القبول:** C28–C29، مع خادم يقدم ملفين مختلفين بنفس الحجم وبصمتين مختلفتين.

## 8. طريقة التحقق والبناء

ابدأ باختبار يعيد السلوك الخاطئ إن أمكن، ثم أصلح أصغر مساحة لازمة، ثم شغّل الاختبارات المتأثرة. استخدم Fixtures وخادم الاختبار الحاليين بدل إنشاء منظومة موازية. لا تستخدم النوم الحقيقي الطويل لإثبات Retry-After أو سباق زمني.

المهام التي نجحت سابقًا، من جذر التطبيق، مثال على Windows PowerShell:

```powershell
.\gradlew.bat :downloader:core:desktopTest :downloader:monitor:desktopTest :shared:app:desktopTest :desktop:app:compileKotlin
```

راجع Workflow الفعلي ونسخة Gradle/JDK وتكوين المنصة قبل النسخ؛ لا تفترض أسماء المهام لأي اختبار جديد في `integration/server` أو الإضافة. شغّل مهمة packaging الفعلية الموجودة التي استدعت `createReleaseFolderForCi` وNSIS في البناء الناجح بعد تحديد مسارها الحالي، ولا تخترع أمرًا مضمونًا بلا فحص.

داخل كل دفعة، اجمع التعديلات التابعة في Commit متماسك يمر بالبناء، ثم اختبارات الدفعة. عند تغييرات دورة الحياة/الحفظ/API شغّل مجموعات الارتداد ذات الصلة، وقبل RF11 شغّل المجموعة الكاملة والحزمة. لا تعِد البناء الكامل بعد كل تعديل نصي إذا لم يضف ذلك دليلًا؛ ولا تختصر الاختبارات الضرورية لتجنب الوقت.

احتفظ بالاختبارات الموجودة المفيدة وأضف سيناريوهات الفجوات. اختبار Fake ناجح لا يغني عن HTTP/HLS Job فعلي؛ واختبار ساعة افتراضية لا يغني عن تجربة Sleep/Wake على Windows. اختبارات الثيمات الهيكلية لا تثبت جمال التباين بصريًا. عند فشل بيئي، سجله «محجوب ببيئة» منفصلًا عن فشل التطبيق.

## 9. متى نعتبر بندًا قد أُصلح؟

الحالات المسموحة في السجل: **لم يبدأ ← قيد إعادة الإنتاج ← قيد الإصلاح ← اجتاز آليًا ← اجتاز تشغيل Windows/بصريًا عند الحاجة ← مغلق بدليل**. بدائل واضحة: «غير قابل لإعادة الإنتاج على SHA محدد» أو «محجوب بسبب محدد». لا تنقل R إلى «مُصلح» لأنك عدلت المصدر فقط؛ أثبت الخطر أو أثبت الحارس المطلوب باختبار ذي معنى.

شرط إغلاق كل ملاحظة: مصدر وتغيير معروفان، اختبار قبول مناسب ناجح، عدم تراجع الميزات المجاورة، توافق البيانات القديمة أو ترحيل مجرب، مراجعة الفرق، وتحديث المرجع الأصلي بالدليل. الشرط المرئي/التفاعلي لا يسقط إذا لم تتوفر بيئته؛ اتركه مفتوحًا وواصل مهمة مستقلة.

إعادة إغلاق P2-10 تتطلب RF01a/RF01b وRF02 واختبارات الاستعادة والتصنيفات من RF03، وتحقيق جميع شروط البند الأصلي. نجاح تلك الدفعات لا يغلق T03/T18 تلقائيًا ولا بقية P2. إن كان بعض RF03 يخص مرحلة لاحقة، بيّن بدقة ما يغطيه دليل P2-10 وما بقي مستقلًا؛ لا تستخدم ذلك لإخفاء خطر فساد التصنيفات.

## 10. سجل التنفيذ والاستئناف داخل المرجع الأصلي

في RF00 أضف متابعة موجزة إلى `docs/Download_Manager_Execution_Plan_v1.md`، ثم حدّثها مع كل تقدم محفوظ. إن نُسخ هذا الملحق إلى `docs`، اربطه من المرجع؛ لا تُنشئ مصدرَي حالة مختلفين. استخدم معرفات C للقبول وA/R للملاحظات وP للمتطلبات دون خلط.

قالب كل دفعة:

```text
الدفعة: RFxx — الحالة:
الملاحظات/متطلبات P المرتبطة:
SHA البداية / فرع الاسترجاع / نسخة بيانات الاختبار:
ما تغير ولماذا / الملفات:
اختبارات C المنفذة والأمر الفعلي:
Passed / Failed / Skipped من التقرير، لا من عدّ @Test:
Commit الكود المختبر / Run / Evidence ID / Artifacts:
نتيجة التوافق مع البيانات القديمة:
ما لم يُختبر وسببه:
التغييرات غير الملتزمة إن وجدت:
الخطوة التالية المحددة والملف/اختبار القبول التالي:
```

قالب نهاية جلسة/قرب امتلاء السياق:

```text
ابدأ من: المستودع القائم، الفرع (...)، HEAD (...).
آخر دفعة مغلقة بدليل: (...).
الدفعة المفتوحة: (...)؛ C المنفذة (...)؛ C المتبقية (...).
العائق/القرار التقني المتخذ وسببه: (...).
آخر اختبار ونتيجته ورابطه: (...).
نقطة استرجاع المصدر/البيانات: (...).
أول إجراء في الجلسة التالية: (...)؛ لا تعِد المنجز.
```

إذا لم يستطع النموذج دفع Commit، لا يصف العمل بأنه محفوظ على GitHub. يذكر الملفات/الفرق المحفوظة محليًا والسبب بدقة، ويحفظ checkpoint ممكنًا دون أسرار. لا يفترض استمرار أي مسار Scratch بعد الانتقال لجلسة أخرى.
